# UI 国际化前期评估与讨论结论

## 文档性质

本文是“大功能 3：多语言，至少英文”的前期评估记录，供真正开始设计和实现时参考。

本文不是最终实现方案，也不代表已经完成全量文案清单。此前按源码汉字匹配得到的 723 处结果混有重复文案、注释、开发日志、协议文字和不应翻译的数据，不能直接当作 723 个翻译项。正式实施前仍需按本文规则重新归并和审计实际 UI 文案。

## 1. 已确认的功能范围

第一版只增加英文，支持：

- 中文；
- 英文。

只国际化应用自身的 UI，包括但不限于：

- 页面静态文字；
- 动态生成的按钮、标签、状态和提示；
- `title`、`aria-label`、`placeholder` 等 UI 属性；
- 应用自己添加的错误前缀和状态说明；
- 帮助、免责声明和确认提示；
- 应用自动生成的默认 UI 名称。

不国际化：

- 用户输入；
- 用户命名的端点、模型、会话、备注等数据；
- 模型输出；
- API 返回的原始错误内容；
- 文件名、目录名、URL、API Key、模型 ID 等数据；
- Markdown 代码块的编程语言；
- ASR 请求中的 `language` 参数及其取值；
- OpenAI、Claude、Gemini、Responses、Base URL、API Key 等品牌名或技术标识；
- 发送给模型的协议占位文字；
- 代码注释和只供开发者查看的诊断日志。

边界判断原则：应用添加的 UI 外壳需要翻译，外部或用户产生的内容保持原样。例如：

```text
修订提示：<模型返回的 revised_prompt>
API 请求失败：<API 原始错误>
```

其中“修订提示”和“API 请求失败”属于 UI；后面的动态内容不翻译。

## 2. 语言切换和生效方式

第一版允许“页面需要刷新才生效”。严谨含义是：

1. 用户选择语言；
2. 程序保存语言偏好；
3. 页面刷新；
4. 页面初始化时读取语言偏好；
5. 整个页面按选定语言渲染。

“页面需要刷新”只定义生效边界，不预先限定必须由用户手动刷新，还是由程序自动刷新。具体交互在正式设计时决定。

建议的语言选择优先级：

```text
已保存的用户选择
→ 没有保存值时，读取浏览器语言
→ 浏览器为英文时使用英文，否则使用中文
```

切换后还需要同步：

```js
document.documentElement.lang
```

中文使用 `zh-CN`，英文使用 `en`。

## 3. 翻译标记如何起效

静态 UI 和动态 UI 都可以使用同一种翻译标记。动态 UI 不需要另设一套国际化机制。

例如：

```html
<button data-i18n="action.send"></button>
```

`data-i18n` 只是普通自定义属性，浏览器不会自动翻译。项目自己的国际化运行时需要：

1. 读取当前语言；
2. 查找带翻译标记的元素；
3. 用 key 查询语言资源；
4. 写入元素文本或属性。

动态 UI 的推荐流程：

```text
克隆或创建元素
→ 元素或模板已经带 data-i18n
→ 插入 DOM
→ 对新生成的根节点执行翻译
```

短暂存在、没有对应持久 DOM 节点的即时字符串，可以直接调用同一翻译层的 `t(key, params)`。例如：

```js
showMessage(t('storage.importFailed'));
```

`data-i18n` 和 `t()` 是同一套翻译资源的两种入口，不是静态 UI 与动态 UI 的两套系统。

带变量的翻译必须把 key 和动态值分开：

```text
endpoint.testing = "正在测试 {count} 个端点"
```

端点名、模型名和 API 原始错误等动态值只插入占位位置，不作为翻译 key，也不翻译其内容。

第一版既然刷新后生效，语言切换时不需要遍历并即时重绘当前页面的全部动态 UI。刷新后，各模块按已保存语言重新创建界面即可。

## 4. 图标问题暂不纳入本轮国际化优化

本轮不以“改成图标”减少翻译量。

即使控件使用图标，仍需提供并翻译：

- `title`；
- `aria-label`；
- 危险操作的确认文案；
- 可能被误解的状态说明。

图标只能减少可见文字或改善布局，不能消除国际化需求。是否继续图标化应作为独立的 UI 任务评估，不与第一版英文支持绑定。

## 5. 文案审计原则

### 5.1 不为了英语压缩中文

正确顺序是：

```text
语义完整
→ 中文自然
→ 英文自然
→ 处理英文长度和布局
```

不能因为英文占地较大，就删除中文中的对象、条件、状态或指标类型。英文过长应优先通过以下方式解决：

- 使用自然的英文惯用表达；
- 缩写非歧义词；
- 允许换行；
- 调整弹窗、字段标签和按钮组布局；
- 把补充说明放到合适的说明区或 tooltip；
- 在不损失语义的前提下删除重复上下文。

### 5.2 只省略非关键词

每条文案审计前先判断：

1. 它描述的对象是什么；
2. 它表达的是动作、状态、条件、时间还是免责声明；
3. 哪些词承担对象和语义限定；
4. 删除某个词后，用户面对真实值时是否仍能准确理解；
5. 它是否真的在用户可见路径中出现。

可以删减：

- 已由当前位置明确表达的重复上下文；
- 不提供新信息的宣传性修饰；
- 同一句中重复出现的状态前缀；
- 不影响对象、动作和条件的赘词。

不能删减：

- 对象名称，如“目录”“端点”“嵌入”；
- 对象限定，如“嵌入维度”中的“嵌入”；
- 状态主体和数量，如“3 个端点思考中”；
- 时间指标类型，如首响时间、总耗时、思考耗时；
- 可用条件中的具体字段；
- 免责声明中的风险和行动建议。

### 5.3 真实值测试

不能用 `[路径]`、`[名称]` 这种带类型信息的抽象占位符判断文案是否清楚。必须代入可能出现的真实值，例如：

```text
当前存储目录：test
当前存储目录：aaa
```

“存储：test”无法说明 `test` 是目录名，因此“目录”是关键词，不能删除。

### 5.4 先追踪显示路径，再决定是否需要翻译和优化

字符串出现在源码中，不代表它一定会被用户看到。需要检查：

- 元素初始是否隐藏；
- 文案在显示前是否会被覆盖；
- 哪个状态会触发；
- 是否只进入模型请求或开发日志；
- 是否在多个渲染路径中重复出现。

正式审计表应使用以下结构，而不是简单的“能否精简”：

| 原文 | 实际显示路径 | 语义关键词 | 可删的仅限冗余 | 英文候选 | 英文布局处理 |
|---|---|---|---|---|---|

## 6. 已讨论并纠正的具体文案

### 6.1 当前存储目录

源码位置：[src/layout.html](../../../../src/layout.html)。

中文保留：

```text
当前存储目录：
```

其值只是相对路径最后一截，可能是 `aaa`、`test` 等，值本身不能说明它是目录。不能缩成“存储”。

英文需要保留 current、storage、directory 三层含义；可通过缩写控制宽度，例如：

```text
Cur. storage dir:
```

这只是候选，最终要结合项目英文风格和真实布局验证。

### 6.2 复制与复刻

中文区分：

- “复制”用于复制消息、内容、代码、向量等；
- “复刻”用于根据现有端点创建一个新的端点节点。

不能为了英文统一而把“复刻节点”改成“复制节点”。翻译资源也应使用不同 key，例如：

```text
action.copy
endpoint.duplicate
```

### 6.3 用户消息中的“我”

源码位置：[src/layout.html](../../../../src/layout.html) 的用户消息模板。

中文保持“我”。英文聊天界面可使用 `You`，因为界面从系统对用户说话的角度标记“你的消息”；也可以在正式英文审校时比较 `You` 与 `Me`。这属于英语语用选择，不是为了缩短中文，也不改变中文文案。

### 6.4 分叉

按钮位于具体用户消息上，位置已经表达“从此处”。中文保留“分叉”，不扩写为“从此处分叉”。

英文候选为 `Fork` 或 `Branch`，正式实施时根据产品术语统一选择。

### 6.5 思考与 Reasoning

响应卡片里的“思考”是内容区标题，英文优先使用：

```text
Thinking
```

`Reasoning` 更适合 API 能力或参数术语，例如 Responses 的 `reasoning_effort`。不能因为参数使用 reasoning，就把所有 UI 中的“思考”统一翻译成 `Reasoning`。

### 6.6 等待思考

[src/layout.html](../../../../src/layout.html) 的流式响应模板中存在：

```text
等待思考...
```

但它位于初始隐藏的思考块内。当前更新流程只有收到真实思考内容时才显示该块，并会用实际思考内容覆盖占位文本。因此它是隐藏模板占位，不应按常驻可见 UI 评估。正式实现时仍需通过真实运行路径确认它是否可能短暂显示，再决定是否保留对应翻译 key。

“等待回复...”位于流式响应卡片的可见正文区域，属于明确需要国际化的初始状态。

### 6.7 嵌入维度

中文保持：

```text
嵌入维度：
```

不能缩成“维度”，因为“嵌入”限定了该数值属于什么。英文候选：

```text
Embedding dimensions:
```

如果英文过长，应调整该结果区域的布局，而不是删除关键词。

### 6.8 修订提示

“修订提示”存在于图像生成结果的两个渲染路径：

- [src/modules/messages.js](../../../../src/modules/messages.js)
- [src/modules/main.js](../../../../src/modules/main.js)

结构为：

```text
修订提示：<模型返回的 revised_prompt>
```

只翻译固定前缀“修订提示”；模型返回的 `revised_prompt` 原样保留。

### 6.9 AI 生成内容免责声明

当前中文：

```text
内容由AI生成，请仔细甄别使用
```

该句同时表达内容来源和使用建议，不能为适应英文布局随意压缩。英文应寻找自然、成熟的免责声明表达，再通过布局解决长度问题。

已找到但尚未最终确认的英文候选：

```text
AI-generated content may be inaccurate. Please verify important information.
```

另一个更口语化的常见表达是：

```text
AI can make mistakes. Check important info.
```

最终选择需要同时比较：

- 是否保留“内容由 AI 生成”的来源说明；
- 是否准确对应“请仔细甄别使用”；
- 产品整体语气；
- 流式提示栏能否正常换行和容纳。

参考来源仅用于英文惯用表达，不代替产品语义判断：

- [Microsoft Dynamics 365 Implementation Portal](https://implementationportal.dynamics.com/) `[需验证]`
- [Chatbox AI](https://web.chatboxai.app/) `[需验证]`
- [New York State Acceptable Use of Artificial Intelligence Technologies](https://its.ny.gov/system/files/documents/2026/07/nys-p24-001-acceptable-use-of-ai.pdf) `[可信]`

### 6.10 多端点思考状态

中文保持自然、完整的状态：

```text
3 个端点思考中
```

不能改成“3 个生成中”，因为会丢失“端点”和“思考”两个关键词。

英文可采用简短的状态短语：

```text
3 endpoints thinking
```

英文是否需要 `are`，应按整体 UI 的状态短语风格统一决定。

### 6.11 时间信息

当前 UI 至少存在三类不同指标：

- 首次响应时间；
- 总耗时；
- 思考耗时。

不能只显示裸时间值。每个数值必须让用户知道它表示什么，例如：

```text
反应 1.2s
耗时 3.4s
思考耗时 0.8s
```

英文应在保留指标语义的前提下优化，例如：

```text
First response: 1.2s
Total: 3.4s
Thinking: 0.8s
```

具体英文术语需要结合代码中 `firstTokenTime` 的真实定义确认，“反应”是否最终改为“首响”属于独立中文文案决策，不能由英文长度反推。

### 6.12 录音状态

如果开始动作统一使用“录音”，停止动作应成对使用：

```text
录音
停止录音
```

不能混用“录音”和“停止录制”。英文候选：

```text
Record
Stop recording
```

### 6.13 必填与选填

不在每个可选字段后重复写“选填”。采用传统必填标记：

```text
名称 *
类型 *
模型名
Base URL
API Key
备注
```

实施前必须先根据实际校验逻辑确认哪些字段真正必填，不能为了布局假设必填关系。必要时在表单中说明 `*` 表示必填。

### 6.14 接口风格中的“某某式”

当前中文使用：

```text
ChatGPT式
Claude式
Gemini式
即梦式
Responses式
```

“式”表达采用某种接口格式，不能未经产品和代码语义确认就删成单独的品牌名。英文应翻译这种关系，而不是只保留 `Claude`、`Gemini` 等名称。

英文候选形式：

```text
ChatGPT-style
Claude-style
Gemini-style
Jimeng-style（名称待确认）
Responses-style
```

“即梦式”对应的英文产品名尚未确认，`Jimeng-style` 只用于表明不能漏掉该项，不是最终译名。最终名称需要结合实际协议兼容含义确认。不能擅自把“OpenAI、国内主流”改写成 `OpenAI-compatible`，除非代码和产品定义确认二者等价。

### 6.15 节点可作为端点的条件

当前说明明确列出具体字段：

```text
若 baseUrl、接口风格、API Key、模型名都存在（含继承），则该节点可作为端点使用
```

不能缩成“必要配置齐全后”，否则用户不知道必要配置是什么。

可考虑更紧凑但仍完整的表达：

```text
baseUrl + 接口风格 + API Key + 模型名（均可继承）→ 可用端点
```

或：

```text
baseUrl、接口风格、API Key、模型名均已设置（包括继承）后，该节点才能作为端点使用。
```

英文也必须保留四项条件。

## 7. 英文布局的重点验证区域

以下区域不是要删除中文关键词，而是实施英文时需要专门做布局验证：

1. 顶栏“当前存储目录”及真实短目录名；
2. 流式提示栏中的免责声明、多端点思考状态和全部停止按钮；
3. 端点编辑弹窗中的字段标签、类型和接口风格选项；
4. 会话参数的三态选项和说明；
5. 连接测试摘要、失败状态及长错误；
6. 参数名称、placeholder 和校验提示；
7. 嵌入结果中的“嵌入维度”；
8. 响应卡片中的首响、总耗时和思考耗时。

布局问题的处理优先级：

```text
自然英文表达
→ 合理缩写非关键词
→ 允许换行或扩展宽度
→ 调整布局结构
→ 最后才考虑删除真正重复的信息
```

## 8. 正式实施前的重新审计要求

正式开始时，不沿用“723 条 UI 文案”的说法。应执行以下流程：

1. 扫描 HTML 和 JS 中可能面向用户的文字；
2. 排除注释、日志、协议文字、用户数据和外部动态内容；
3. 按语义归并重复文案为翻译 key；
4. 追踪每条文案的实际显示路径；
5. 分别记录文本内容、`title`、`aria-label`、`placeholder`；
6. 用真实值测试上下文是否足够；
7. 为英文提供自然候选，不反向修改中文；
8. 标出英文布局风险，但把布局修复和中文精简分开决策；
9. 对危险确认、免责声明、配置条件和错误说明做人工复核；
10. 在源码版、单页面 HTML 和 Chrome 扩展中分别验收。

## 9. 待正式设计时确认

以下事项尚未最终决定：

- 语言选择后由程序自动刷新，还是只提示页面需要刷新；
- 首次没有保存值时，是否采用“浏览器为英文则英文，否则中文”的默认规则；
- 语言选择控件放置位置；
- 翻译资源的文件格式和模块加载顺序；
- `data-i18n` 对文本、`title`、`aria-label`、`placeholder` 的具体属性格式；
- 缺失英文 key 时的回退和开发期报警方式；
- “当前存储目录”的英文是否采用 `Cur. storage dir:`，以及缩写风格是否与全局一致；
- 英文中 `You` 与 `Me` 的最终选择；
- “分叉”使用 `Fork` 还是 `Branch`；
- 多端点思考状态是否采用无 `are` 的状态短语；
- `firstTokenTime` 的准确产品含义，以及中文使用“反应”还是“首响”；
- 接口风格各项（包括“即梦式”）的最终英文术语；
- AI 免责声明的最终英文惯用表达；
- 应用自动生成并保存的“新会话”“副本”“分叉”等名称，在切换语言后如何处理已有数据；
- 哪些字段实际必填，从而应用 `*` 标记；
- `等待思考...` 在真实运行中是否可见，是否需要保留。

## 10. 本轮不做的事

- 不实现国际化；
- 不新增英文资源；
- 不修改现有中文文案；
- 不修改图标；
- 不修改版本号；
- 不构建产物；
- 不把本文当作最终实施计划。
